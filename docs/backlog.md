## 우선 처리 — 76 거점 전환 직후의 미해결 결함

### 0. 76 거점 판의 밸런스 (최우선)

거점을 16개에서 76개로 늘린 직후다. 16 거점에 맞춰 둔 수치가 그대로 성립할 리 없고,
실제로 성립하지 않는다. 아래는 **20회 자동 대전 기준이며, 집계 수정(R03) 이전
자료다** — 당시 「승률」은 시간 초과 우세를 포함한 값이고, 전투·함락 수는
로그 600개 절단으로 과소 집계되어 있었다. 현재 수치는
[기준 측정](baseline-642.md)을 볼 것:

| 세력 | 승률 | 시작 → 평균 최종 거점 |
|---|---|---|
| 고구려 | 55.0% | 27 → 29.4 |
| 백제 | 0.0% | 17 → 17.1 |
| 신라 | 45.0% | 32 → 29.0 |

결착률 26% → **0%**. 40년을 돌려도 거점이 두세 개밖에 오가지 않는다.

짚이는 원인:
- AI 의 동시 원정군 수가 `거점 수 ÷ 2` 라 고구려는 13 이 되는데, 판이 5배 넓어져
  한 부대가 전선에 닿는 데 걸리는 턴수도 함께 늘었다. 부대가 길 위에서 시간을 다 쓴다.
- 수입도 거점 수에 비례하므로 세 나라 모두 예전보다 훨씬 부유하다.
  병력 상한이었던 병영 수용량이 더 이상 제동 장치가 아니다.
- 산성 방어 배율을 받는 거점을 15개로 한정했는데도, 76개를 다 치기에는 턴이 모자란다.
  160턴(40년)이 짧은 것인지 진격이 느린 것인지부터 갈라야 한다.

`npm run simulate` 의 "시작 → 평균 최종 거점" 표가 이 작업의 계기판이다.
승률보다 이 수치가 먼저 움직여야 한다.

### 1. 551년 시나리오의 백제 승률 3.3%

목표 구간은 25~40%. 원인으로 짚이는 것:

- 4거점으로 시작하는데 현재 AI 는 영토 규모에 비례해 눈덩이처럼 커진다
  (동시 원정군 수 = 거점 수 ÷ 2, 수입도 거점 수에 비례).
- 553년 「한강의 배신」과 554년 「관산성의 화살」을 연달아 맞는다.
  후자는 성왕(통솔 88·정치 93)을 잃는 것이라 타격이 크다.

시도해 볼 만한 방향:
- 작지만 부유한 세력이 버틸 수 있게 하는 구조 — 예컨대 거점당 개발 상한을 높여
  "적은 성을 깊게 키우는" 길을 열어 준다.
- 백제의 `dual_diplomacy`·`wa_alliance` 특성을 실제 수치로 구현
  (현재 `maritime_trade` 만 동작한다. `formulas.ts` 의 `TRAITS` 참조).
- 왜의 파병 이벤트를 백제 전용 구원 수단으로 추가.

**이미 시도했다가 되돌린 것**: "벅찬 전선이면 화평을 청한다"는 AI 규칙.
약자가 웅크리는 동안 강자가 무저항으로 커져 오히려 악화됐다 (CHANGELOG 참조).

### 2. AI 대전 결착률 26%

(거점 16개 시절 수치다. 76 거점 판의 현재 결착률은 [기준 측정](baseline-642.md)에 있다.)

나머지 74%는 160턴(40년) 시간 초과다. 두 세력이 남은 뒤 서로를 끝내지 못한다.
사람이 플레이할 때는 덜 두드러지지만, 밸런싱 지표로서는 표본이 얕아진다.

### 3. 단계 A 에서 일부러 남긴 것

결과를 바꾸는 규칙 변경이라 결함 수정과 섞지 않았다. 각각 따로 재고 나서 정한다.

- **항구 수비대의 수군 몫이 강등된다.** `naval` 적성 장수가 없으면 그 몫이
  육상 보병이 되어 조용히 사라진다. 무지휘 수군(통솔 40)으로 세우는 편이
  §3.5 「장수가 없어도 수비대는 존재한다」와 맞지만, 모든 항구 공성의 결과가
  달라지므로 따로 잰다.
- **주둔 수비대 구성표가 실제 징병을 보지 않는다.** 그 성에서 무엇을
  징병했든 거점 유형이 계열을 정한다(§3.5 의 결정). 징병을 반영하려면
  별도 설계가 필요하다.
- **「전 거점의 3분의 2 장악」 패권 규칙.** 진행률 계산에만 있고 판정에도
  기획서에도 없어서 뺐다. 결착률을 올리는 손잡이로 쓸지는 따로 판단한다.
- **수군 단계 사다리** (어선단·병선·누선, 전투 기획서 §2.1). 수군은 지금
  보병 단계를 빌려 쓴다.

## Phase 4 잔여 (M2)

- **천도** — 고구려 국내성→평양, 백제 한성→웅진→사비. 재화 소모 + 수 턴 혼란 + 국가 보정 변경.
  거점 등급을 동적으로 바꿔야 해서 `CastleDef.type` 을 상태로 옮기는 작업이 선행된다.
- **내응의 사전 공작과 실패 대가** — 내응 자체는 **구현되어 있다**
  (`src/core/field/siege.ts`, 자동 대전 함락의 3.5%). 지금은 실패해도 비용이
  없어 AI 가 이른 시점에 눌러 본다. 사전 공작·발각 시 경계 강화가 남았다 (G07).
- **수공·화공의 전략적 준비** — 전투 중 발동은 **구현되어 있다**
  (`field/orders.ts` 화계·수계, `field/siege.ts` 수공·화공·소성. 함락의 10.3%).
  남은 것은 계절·지형 준비를 전략맵에서 미리 하는 경로다.
- **외세 침공 전용 AI** — 지금은 이벤트 효과 `invasion(tang, 60000)` 으로 국경 거점에
  피해를 주는 간이 스크립트다. 계획서 §3.4 가 말한 "일반 AI 와 다른 이벤트성 대군" 로직은 없다.
- **왜의 백강 파병, 말갈 약탈** — 비대칭 이벤트 병력.
- **혼인 동맹, 원군 요청** — 외교 명령 중 미구현분.
- **화랑도 성장형 인재** — 지금은 아직 등장 연도가 안 된 인물을 앞당겨 발탁하는 형태다.
  진짜 절차 생성 인물(이름·능력치 생성 + 경험치 성장)은 없다.

## 모바일 — M단계에서 남긴 것

폰에서 한 판을 끝까지 둘 수 있게 된 뒤에도 남은 것들이다. 막는 결함은 아니다.

- **실기기 확인을 못 했다.** 여기서 한 것은 Playwright 의 모바일 에뮬레이션이다.
  실제 iOS Safari 의 주소창 접힘, `100dvh` 의 순간 값, `env(safe-area-inset-*)`,
  탭 지연은 다를 수 있다. 노치 있는 기기에서 한 번은 눈으로 봐야 한다.
- **축소된 축척에서 거점 탭이 모호하다.** 터치 원은 화면 좌표로 44px 고정인데
  반도 전체가 들어오는 62% 축척에서는 거점 사이가 20px 도 안 되어 이웃과 겹친다.
  겹칠 때 위에 그려진 것이 아니라 **가장 가까운** 거점이 잡히게 하면 낫다
  (지금은 SVG 히트 테스트에 맡겨 두어 그리는 순서가 이긴다).
- **세로 전투에서 육각판 위아래가 남는다.** 13×9 판은 가로로 길어 세로 화면에서는
  폭에 맞춰 그려지고 위아래가 빈다. 판을 돌리거나 세로용 축척을 따로 두는 방법이 있다.
- **첫 짐이 무겁다.** 한 덩어리 681KB(gzip 201KB)에 `officers.json` 149KB 가
  통째로 먼저 온다. 시나리오별로 갈라 실으면 폰의 첫 화면이 빨라진다.
- **`panBy` 가 포인터 이동마다 DOM 을 즉시 고친다.** 지금 측정으로는 폰에서도
  60fps 바닥이라 문제가 아니지만, 레이어가 더 늘면 rAF 로 합쳐야 한다.
- 영향권 블러는 **재고 나서 그대로 두기로 했다** — CPU 6배 조임 폰 프로파일에서
  지도를 끄는 동안 프레임 중앙값이 켬 17.2ms / 끔 16.7ms 로 차이가 잡음 안이다.
  나중에 느려지거든 이 측정부터 다시 한다.

## 기술 부채

- `scripts/test.ts` 는 프레임워크 없는 자체 assert 다. 테스트가 더 늘면 vitest 도입 검토.
- `src/core/data.ts` 가 시나리오를 정적 import 한다. 시나리오가 많아지면 glob import 로 바꾼다.
- 전투 UI 의 `reachable()` 이 매 렌더마다 다시 계산된다. 부대 수가 늘면 캐시가 필요하다.
- Godot 4 이관 검토 (계획서 §5). 코어가 React 를 전혀 모르므로 로직은 이식 가능하지만,
  TypeScript → GDScript 는 사실상 재작성이다.
