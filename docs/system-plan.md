> 이 문서는 개발의 설계 근거가 된 원본 계획서다. 실제 구현이 이 계획과 갈라진 지점은

기획서(v1) 기반 개발 설계 문서. 전제: 1인 개발, Claude Code 활용, M1 웹 프로토타입 → 검증 후 확장.

## 1. 전체 아키텍처

### 1.1 설계 원칙
- **데이터와 로직의 완전 분리**: 인물·거점·이벤트는 전부 JSON 데이터 파일. 밸런싱은 코드 수정 없이 데이터만 고쳐서 수행 (비개발자가 직접 만질 수 있는 영역을 최대화)
- **턴제 = 상태기계**: 실시간 요소가 없으므로 게임 전체를 "상태(State) → 명령(Command) → 새 상태" 순수 함수 구조로 설계. 버그 추적과 세이브/로드가 단순해짐
- **모듈 독립성**: 전투 모듈은 전략 모듈 없이 단독 실행 가능하게 (전투만 따로 테스트하기 위함)

### 1.2 모듈 구성도

```
┌─────────────────────────────────────────────┐
│                 UI 레이어 (React)             │
│  전략맵 화면 │ 내정 패널 │ 전투 화면 │ 외교/인물 │
└──────────────────┬──────────────────────────┘
                   │ (명령 전달 / 상태 구독)
┌──────────────────┴──────────────────────────┐
│              게임 코어 (순수 JS/TS)            │
│ ┌─────────┐ ┌─────────┐ ┌────────────────┐  │
│ │ 턴 엔진  │ │ 내정 모듈 │ │ 전투 모듈(헥스)  │  │
│ ├─────────┤ ├─────────┤ ├────────────────┤  │
│ │ AI 모듈  │ │ 외교 모듈 │ │ 이벤트 엔진     │  │
│ ├─────────┤ ├─────────┤ ├────────────────┤  │
│ │ 인물 모듈 │ │ 경제 모듈 │ │ 저장/로드      │  │
│ └─────────┘ └─────────┘ └────────────────┘  │
└──────────────────┬──────────────────────────┘
                   │ (읽기 전용 참조)
┌──────────────────┴──────────────────────────┐
│              데이터 레이어 (JSON)              │
│ 세력 │ 거점 │ 인물 │ 병종 │ 이벤트 │ 시나리오    │
└─────────────────────────────────────────────┘
```

```json
{
  "id": "hangang_betrayal",
  "name": "한강의 배신",
  "trigger": { "year": 553, "condition": "alliance(silla, baekje) AND owns(silla, hangang_upper)" },
  "choices": [
    { "text": "동맹을 깨고 한강 하류를 기습한다", "effects": ["break_alliance", "war(baekje)", "cause:-20"] },

```
※ 이벤트는 코드가 아닌 데이터로 작성 → 이벤트 100종 확장 작업이 "JSON 작성 작업"이 됨. Claude에게 사료를 주고 이벤트 JSON을 뽑게 하는 파이프라인 구축 가능.

### 2.5 시나리오 (scenarios/*.json)
- 시작 연도, 세력별 거점 소유 매핑, 인물 배치, 초기 자원, 활성 이벤트 목록만 정의
- 시나리오 추가 = JSON 1개 추가 (시스템 수정 없음)

## 3. 핵심 모듈 상세

### 3.1 턴 엔진 (모든 모듈의 지휘자)
```
1턴(1계절) 처리 순서:
① 플레이어 명령 입력 수집 (내정/군사/외교/인사)
② AI 세력 명령 생성
③ 명령 일괄 해석(resolve) — 이동 충돌 → 전투 발생 판정
④ 전투 처리 (수동 전투면 전투 화면 진입, 위임이면 자동 계산)
⑤ 이벤트 트리거 검사 → 발생 이벤트 처리
⑥ 결산: 수입, 병량 소모, 민심·지지도 변동, 인물 사망/등장
⑦ 상태 저장 → 다음 턴
```
- 구현 핵심: `gameState`(전체 상태 객체) + `applyCommand(state, cmd) → newState` 패턴
- 계절 효과: 겨울(압록강 결빙=도하 가능, 병량 소모↑), 가을(수확), 여름(장마=수공 보정)

### 3.2 내정 모듈
- 명령: 개발(농/상/성곽/병영), 징병, 훈련, 순찰(민심), 탐색(인재), 제도 반포, 천도
- 각 명령 = `{담당 인물, 대상 거점, 비용, 계산식}`
- 계산식 예: `농업개발량 = 기본 10 × (담당자 정치/100) × 민심계수`
- **계산식은 전부 formulas.js 한 파일에 모음** → 밸런싱 시 이 파일만 수정

### 3.3 전투 모듈 (헥스 턴제)
- 헥스 그리드: 전투맵 15×11 (프로토타입은 9×7로 축소)
- 유닛 = `{장수, 병종, 병력수, 사기, 훈련도}`
- 데미지 공식(초안): `피해 = 병력 × 병종상성 × 지형계수 × (공격장수 통솔·무력 가중) − 방어측 경감`
- 전투 종료: 한쪽 전멸/퇴각/30턴 경과(공성은 공격 실패 처리)
- 공성 전용 규칙: 성벽 HP, 공성병기 유닛, 병량 카운트다운(포위전), 내응 발동
- **단독 실행 모드 필수**: 전략 파트 없이 "전투 시뮬레이터" 페이지로 따로 테스트

### 3.4 AI 모듈 (프로토타입은 단순 규칙 기반)
3단계 우선순위 휴리스틱으로 시작:
```
1순위: 생존 — 침공받는 중이면 방어·원군
2순위: 성장 — 최저 개발 거점에 투자, 병력 열세면 징병
3순위: 확장 — 인접 거점 중 (방어력/거리/외교관계) 점수 최저 목표 공격
```
- 세력 성향 파라미터: `공격성, 확장욕, 외교선호` (고구려 공격적, 신라 외교적 등)
- M3에서 외세(수·당) 침공 스크립트 AI 별도 추가 (일반 AI와 다른 "이벤트성 대군" 로직)

### 3.5 외교 모듈
- 관계값: 세력 쌍마다 `우호도(-100~100)` + `상태(전쟁/화평/동맹/조공)`
- 명령: 동맹 제의, 파기, 조공(대중국), 혼인, 원군 요청, 선전포고(명분 소모)
- 성공 판정: `우호도 + 사절 매력·지력 보정 + 제안 이익 평가 ≥ 임계값`
- 귀족회의: 대형 결정(천도·제도·선전포고) 시 지지도 판정 → 실패 시 시행 불가 or 강행(정변 리스크 플래그)

### 3.6 이벤트 엔진
- 매 턴 ⑤단계에서 events.json 전체를 트리거 조건 평가
- 조건식 파서: `year`, `owns()`, `alliance()`, `flag()`, `stat비교` 정도의 미니 DSL
- 역사 이벤트 ON/OFF 옵션은 이벤트 목록 필터링으로 구현

### 3.7 저장/로드
- gameState 전체를 JSON 직렬화 → 파일 다운로드/업로드 방식(웹) → Steam 빌드 시 로컬 저장 전환
- 상태기계 구조 덕분에 "리플레이(명령 로그 재생)" 디버깅 기능도 저비용 구현 가능

## 6. 개발 순서 (Claude Code 작업 단위)

각 단계 = Claude Code 세션 1~수 회 분량의 작업 단위로 분해. **순서 자체가 의존관계**임.

### Phase 0. 뼈대 (1~2주)
1. 프로젝트 셋업 + 데이터 스키마(TypeScript 타입) 확정
2. 거점 10개·인물 30명·세력 3개 샘플 JSON 작성
3. gameState 구조와 저장/로드

### Phase 1. 전략 루프 (3~4주)
4. 전략맵 렌더링(거점 노드+세력 색)
5. 턴 엔진 골격 (명령 수집→결산)
6. 내정 명령 4종 (개발/징병/순찰/탐색) + formulas.js
7. 결산 화면 — **여기까지가 "내정만 있는 게임". 이 시점에 1차 재미 점검**

### Phase 2. 전투 (3~4주)
8. 헥스 전투 시뮬레이터 단독 페이지 (유닛 3병종, 지형 3종)
9. 데미지 공식·사기 시스템
10. 전략맵과 연결 (출진 명령 → 전투 → 결과 반영)
11. 자동 전투(위임) 계산기

### Phase 3. 상대방 (2~3주)
12. 규칙 기반 AI (3단계 휴리스틱)
13. 외교 기본 (우호도, 동맹, 선전포고)
14. **여기까지가 M1 프로토타입 완성 = "이길 수 있고 질 수 있는 게임"**

### Phase 4. 삼국시대다움 (M2, 2~3개월)
15. 이벤트 엔진 + 시나리오 5번(642년) 이벤트 20종
16. 공성전 규칙, 귀족회의, 제도 반포
17. 외세 침공 스크립트, 화랑도 육성
18. 연대기, 승리 조건 판정

### Phase 5. 콘텐츠 양산 (M3)
19. 거점 60개·인물 300명·이벤트 100종 데이터 작업 (사료→JSON 파이프라인)
20. 전 시나리오, 밸런싱, 아트 교체

## 7. 테스트·밸런싱 계획

- **자동 시뮬레이션**: AI끼리 100회 대전시켜 세력별 승률 집계 → 승률 25~40% 범위 벗어나면 formulas.js 조정 (상태기계 구조라 헤드리스 실행 가능)
- **체감 테스트 체크리스트**: "1턴 조작이 3분을 넘는가 / 내정이 클릭노동으로 느껴지는가 / 열세 세력으로 역전 경로가 보이는가"
- 밸런싱 변수는 전부 데이터·formulas.js에 있으므로, 테스트→수정 사이클을 코드 재작성 없이 반복

## 8. 관리 원칙 (1인 개발 리스크 대응)

- **범위 방어**: Phase 4 이전에는 어떤 신규 시스템도 추가 금지 (일기토·문화 시스템 등 유혹 항목은 백로그에만 기록)
- **매 Phase 종료 시 배포**: GitHub Pages에 올려 실제 브라우저에서 플레이 — "돌아가는 최신 버전"을 항상 유지
- **데이터 검증기 우선 제작**: JSON 오타가 최대 버그 원인이 될 것이므로, 스키마 검증 스크립트를 Phase 0에서 먼저 만듦
- **의사결정 기록**: 계산식·밸런스 변경 사유를 CHANGELOG에 남김 (수치를 왜 바꿨는지 잊는 것이 1인 개발 최대 함정)
